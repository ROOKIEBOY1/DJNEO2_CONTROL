# 开发基地1

从 `DJ/DJINEO2` 提取的 HarmonyOS Stage 模型工程，保留原应用页面、协议、通信、控制和离线自检代码。原项目没有修改；独立核心源码快照位于同级 `核心代码` 目录。

## 打开与构建

1. 在 DevEco Studio 中打开此目录，配置 HarmonyOS SDK 26.0.0，并按提示同步依赖。
2. 在项目签名设置中配置当前开发者的证书和设备；此工程故意没有复制原机器的签名材料或本地路径。
3. 构建并在兼容设备上运行。首页可先运行离线自检，再检查飞机 Wi-Fi 连接。

本工程未携带旧构建产物或缓存。是否可编译、安装及与飞机通信，需在当前环境重新验证。摇杆布局、轴向和起降命令的真机行为仍未由本次迁移验证。

## Python 握手实验

`tools/handshake_probe.py` 可预览或发送**一次** 48 字节握手，只等待飞机的 15 字节短包。它不包含摇杆、起飞或降落命令。默认只预览：

`python tools/handshake_probe.py --session 0x4a8c`

真机实验需要电脑连接飞机 Wi-Fi，并先查到电脑的 `192.168.2.x` 地址。只有显式加入 `--send --local-ip <电脑地址>` 才会发包；目标固定为 `192.168.2.1:9003`。脚本默认生成新的、按 8 对齐的头部字；四次抓包中该字都比同会话首个视频包序号少 8，但其生成方尚未确定。没有回复并不意味着飞机不支持独立客户端；也可能是该字段、会话号、连接限制或其他握手条件不符合。

电脑仅靠 Wi-Fi 上网时，切换飞机热点会中断外网。可在断网状态下从工作区根目录运行 `.\.抓包环境\Scripts\python.exe .\开发基地1\tools\run_handshake_offline.py`；它自动读取电脑的 `192.168.2.x` 地址，在同一个 UDP socket 上最多重发 60 次握手（每次间隔约 0.55 秒，总计约 33 秒），把原始回复和结果写入 `captures/handshake-probe-*.json`。之后切回原网络即可查看或分享结果。这个 Python 入口不受 PowerShell 脚本执行策略影响。

离线验证：在 `tools` 目录运行 `python -m unittest discover -v`。握手逐字节样本、短包解析和本机 UDP 收发均在测试中覆盖。

可运行 `.\.抓包环境\Scripts\python.exe .\开发基地1\tools\diagnose_handshake.py`，并在 Windows 弹窗中批准管理员权限；脚本会在新窗口记录电脑网卡流量。它仍只发送握手，最多持续约 33 秒；收到匹配短包后会继续被动监听 2 秒，统计后续通道。结果保存为 `captures/handshake-diagnostic-*.json` 与 `.pcapng`。网卡捕获在一次成功实验中漏记了已被 Python socket 收到的短包，因此回复判断应以 JSON 为准。PCAPNG 可能包含其他网络流量，分享前应先筛选。

握手已验证后，可在飞机停留地面时运行 `.\.抓包环境\Scripts\python.exe .\开发基地1\tools\run_idle_link_offline.py`。它只在收到匹配握手回复后，以约 60 毫秒间隔发送抓包验证过的 34 字节通道 `0x04` 空包 2 秒，再被动监听 3 秒；不会发送摇杆或起飞命令。结果保存到 `captures/idle-link-*.json`。两次真机实验已收到持续的飞机下行数据；停发后三秒内下行未立即中断。

`tools/initial_010a.py` 和 `tools/neutral_stick.py` 分别离线重建连接初期的 18 字节短帧及后期的 28 字节完整帧，均有抓包逐字节测试。它们不是实机发送入口。`tools/stick_transition.py` 可从抓包统计两种帧的时间分布与组合包形态；详情见 `会话分析.md`。

## 电脑手动飞行控制台（起飞、降落实机已验证）

`tools/flight_console.py` 将已抓到的起飞、降落与前进报文接到同一个电脑 UDP 会话，并区分握手回复与飞控命令回复。默认只显示说明，不联网。飞机在安全场地落地、电脑连接飞机 Wi-Fi 后，从工作区根目录运行：

`.\.抓包环境\Scripts\python.exe .\开发基地1\tools\flight_console.py --connect`

程序默认使用可靠传输：命令走 `0x05` 数据包，`0x04` 单独确认接收窗口，记录飞机累计确认位置，并有限重传；未确认的数据超过一秒会停止连接并保存日志。2026-10-29 11:23 的真机记录已确认 558/558 包，起飞和降落均收到匹配序号的飞控 `00` 回复，用户确认两个动作实际完成；用户随后也确认电脑控制前进成功。连接后自动显示“传输确认”“应用注册”及机型回复；只有设备与新鲜视频同时确认才进入操作提示。`--legacy-transport` 可切回此前方式作比较。

方向命令现支持 `前进、后退、上升、下降、左移、右移、左转、右转`，例如 `左移0.5` 或 `左移 0.5秒`；只写方向时默认执行 0.5 秒，最长 10 秒，每次只改变一个轴，完成后立即四轴回中。`回中` 可单独重发中位指令。只有起飞已获飞控确认才能执行方向；下行静默一秒或请求降落时会回中并停止动作。**新方向尚未全部实机逐项验证；下降不等于降落，回中不保证飞机立即停止。** 程序默认不再定时降落；仍保留输入退出时尝试降落。需要定时降落时可显式加入 `--auto-land-after 30`，界面会显示启用时间并在触发时提示。运行结果保存为 `captures/control-attempt-*.json`。全部命令及验证状态见 `飞行控制指令现状.md`。更新代码后需在飞机落地时退出并重新启动控制台。

同一连接内落地后重飞：先收到降落回复并目视确认飞机已落地，再输入 `再次起飞`。该命令表示操作者确认已落地，重置上一轮飞行标志后发送新的起飞指令；随后可继续方向操作。未收到降落确认或设备/视频不新鲜时拒绝重飞。每轮会记录 `flight_cycle`，之前的定时器回调不能影响新一轮。

`profiles/neo2-registration.json` 仅来自本项目自己的 DJI Fly 抓包，包含这台飞机和手机的设备标识。注册器只发送审查过的 12 类模板，并对已知请求按当前请求序号应答；未知请求只记录摘要。`51/13` 的计数器和时间动态生成，状态跟随飞机上报，不强行设为授权状态。该配置不能直接当作其他飞机的通用配置。

11:00 的一次连接暴露了注册请求中正常变化的能力与状态字段，整包摘要匹配导致注册未完成。现在 `51/41` 会解析带长度的能力列表，只确认本端支持的通道；`51/06` 校验本机身份后回显规定字段，尾部状态变化不再使应答失效。该修正已在 11:23 的真机飞行会话中通过初始化验证。降落回复采用直接 DUML 封装，旧解析器漏报“未收到”；现已同时支持直接与隧道回复，并用本次实机记录回放确认。当前完整本机测试 80 项通过。

### 连续重连修正（2026-10-29）

下午多次失败时，握手、可靠传输、注册、视频和遥测都正常，但隧道设备查询无回复；直接发送的注册查询仍有回复。DJI Fly 抓包中的隧道序号在重连前后继续增长，旧控制台却每次随机重置。新版据此将实际线上隧道序号改为跨进程持久保存的完整计数器，封装中的 DUML 序号填低 16 位，并在发送锁内分配，避免倒序发出。首次启动从历史发送日志恢复；状态保存在 `.state/routing-sequence.json`，不要删除或复制旧状态覆盖它。

同一电脑同时只能有一个新版控制台占用该身份；第二个会提示退出旧控制台。程序崩溃后保留已预留的序号段，重开跳过未用号码，不重复使用。修正已通过本机连续重连、低 16 位回绕、进程互斥、历史恢复和丢弃旧序号的模拟测试，但真实飞机的连续重连稳定性仍待复测。初始化仍要求匹配设备回复和新鲜视频，不会仅凭下行数据放行起飞。

**现状限制：**起飞、降落和前进已有用户实机确认；不同开机状态下的稳定性及其余七个方向仍待验证。屏幕上的“已发送”不表示飞机执行；若起飞没有回复，不要连续重发；先目视确认飞机状态，若已起飞则输入 `降落`，若仍在地面则输入 `退出`，再查看保存的结果。

第三次地面会话中，DJI Fly 未连接飞机。电脑两次发送 `查询设备` 均无回复；整个会话只收到基础通道 1 报文，没有视频和丰富遥测。这个结果说明握手短包不等于完整控制会话已建立，目前先不要重复起飞或设备查询。详见 `会话分析.md` 的“电脑设备信息查询”。

已根据 DJI Fly 的新会话抓包增加 `基础查询`：在同一 UDP 包内发送四个零负载设备查询，并等待其中发往 `0x1F` 的同序号回复；它不发送飞行动作。该构造已与抓包中的四条帧逐字节核对并通过本机测试。2026-10-29 的一次真机测试未收到回复，视频和丰富遥测也未出现；单独重复这四条查询没有价值，后续需要先分析其他启动消息。

地面短帧对照工具 `tools/ground_short_comparison.py` 默认只预览。电脑接入飞机 Wi-Fi、飞机静止在地面后，可从工作区根目录运行 `.\.抓包环境\Scripts\python.exe .\开发基地1\tools\ground_short_comparison.py --send`。它依次建立两个新会话：对照轮先发 1 秒空包，再发 2 秒空包；短帧轮先发 1 秒空包，再发 2 秒抓包中的 18 字节短帧。每轮之后被动监听 3 秒。只有握手匹配才进入发送阶段；不会发送 28 字节完整摇杆帧或起飞命令。全部匹配会话的下行 UDP 数据保存为 `captures/ground-short-comparison-*.json`，供后续逐包比较。首次真机对照已完成，短帧轮没有出现可识别的新回复或状态变化；下行包数量不能单独证明短帧被接受，序号生成规则也仍待验证。

## 离线中文语音控制

入口为 `tools/voice_console.py`。先运行 `.\.抓包环境\Scripts\python.exe .\开发基地1\tools\voice_console.py --listen` 只预览识别，再用 `--connect` 连接飞机。连接后需键盘输入“启用语音”才发送语音飞行动作，断网仍可使用。八方向“一点”默认 0.5 秒，指定时间最长 10 秒；米数和角度需要各方向实测标定。语音起飞和再次起飞均说“确认”完成确认，重飞前必须目视确认落地并收到降落回复。完整离线操作、标定和中断说明见 [语音控制使用说明](语音控制使用说明.md)。

## 原生环绕逆向

已从本人 DJI Fly 抓包定位半径 10 米改 2 米的参数写入及读回、原生环绕启动，以及独立补采的主动停止请求和回复。操作者确认停止后悬停。离线构造器为 `tools/circle_protocol.py`，不发送飞机数据，尚未接入语音执行。字段、原始证据、验证和下一步见 [环绕协议逆向记录](环绕协议逆向记录.md)。

独立电脑测试入口：`.\.抓包环境\Scripts\python.exe .\开发基地1\tools\circle_console.py --connect`。固定 2 米，按“准备→环绕→确认”操作，启动可能自动起飞；可输入“停止”“降落”。当前是键盘入口，尚未进行电脑端环绕实飞验证。详见 [使用说明](电脑原生环绕使用说明.md)。普通控制台“状态”也已增加只读主体候选框与任务状态，不能将候选框当成已锁定。

## 结构

- `entry/src/main/ets/pages`：首页、控制台和自检页面。
- `entry/src/main/ets/protocol`：协议编解码、摇杆及命令。
- `entry/src/main/ets/transport`：网络、权限、UDP 和探测。
- `entry/src/main/ets/control`：定时器与离线自检。
- `tools`：原项目的 iOS 抓包辅助脚本。












# 更新：语音原生环绕与视频

电脑端 2 米原生环绕已实飞完成。使用现有离线中文语音引擎：

```powershell
.\.抓包环境\Scripts\python.exe .\开发基地1\tools\voice_console.py --connect --video
```

键盘输入“启用语音”，说“环绕五米”，再说“确认”；“停止环绕”停止任务，“降落”请求落地。默认 2 米，范围 2–10 米，写入后独立读回核对。只有 2 米键盘环绕已实飞确认，新增语音与其他半径待验证。浏览器打开程序显示的本机地址即可看相机，不依赖互联网。详见《语音控制使用说明.md》。
