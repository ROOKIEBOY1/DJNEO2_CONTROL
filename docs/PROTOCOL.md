# 已实现的协议与移植要点

本文描述研究设备上的观测和当前实现，不是 DJI 官方协议规范。除位域说明外，多字节整数均使用**小端**。保留未知字段原值，不按猜测替换。

## 1. UDP 会话和外层包

手机加入飞机 Wi-Fi，本机取得该网络 IP，在本地临时 UDP 端口绑定 socket；握手、上行命令、确认和下行接收必须使用同一会话 socket。默认目标 `192.168.2.1:9003`。不要在每个动作重新建 socket 或重新握手。

对应源码：`outer.py`、`handshake.py`、`flight_controller.py:connect/_read_loop`。

| 偏移 | 字节数 | 已实现解释 |
| --- | --- | --- |
| 0 | 2 | `0x8000 | UDP负载总长度`；解析校验实际长度 |
| 2 | 2 | session：每次新连接使用非零 u16 |
| 4 | 2 | 通道相关的序号；不同通道不要共享一个累计游标 |
| 6 | 1 | 通道/包类型 |
| 7 | 1 | 字节 0–6 的逐字节 XOR |
| 8–15 | 8 | 长包扩展字段，依通道解释 |

握手短回复只有 8 字节头，不能一律跳过 16 字节。

| 通道 | 当前用途 |
| --- | --- |
| `00` | 握手和握手回复 |
| `01` | 下行控制消息、确认位置与遥测 |
| `02` | 下行视频 |
| `03` | 独立可靠数据下行；核心仍维护其连续确认游标 |
| `04` | 状态/累计确认；参考版本中也承载直接摇杆包 |
| `05` | 当前可靠传输上行 DUML |

## 2. 握手

`build_handshake(session, seed)` 生成 48 字节请求；body 常量见 `handshake.HANDSHAKE_BODY`，不要从历史运行日志整体重放旧 session。

- session 非零 u16。
- `new_video_seed()` 生成非零且按 8 对齐的 u16；它也用于可靠传输初始基准。
- 请求字节 8–9 放 seed；10–15 保留 `64 00 64 00 c0 05`。
- 必须收到来自目标 IP/端口、同 session、通道 00、8 字节头且 body 为 `01 0f 00 05 05 40 1f` 的回复。
- 默认最多 60 次、间隔 0.55 秒。次数增加不能解决注册或路由身份错误。

## 3. DUML 内层编码

对应 `duml.py`、`control_packets.valid_frames`。

| 偏移 | 字节数 | 内容 |
| --- | --- | --- |
| 0 | 1 | `55` |
| 1–2 | 2 | 低 10 位长度，含头和 CRC；当前编码高位版本标记 `04` |
| 3 | 1 | 前 3 字节的 CRC8 |
| 4 | 1 | sender |
| 5 | 1 | receiver |
| 6–7 | 2 | 内层请求序号 u16 |
| 8 | 1 | flags：请求样本常见 `40`，回复需核对回复标志 |
| 9 | 1 | command set |
| 10 | 1 | command id |
| 11… | 可变 | payload |
| 末 2 字节 | 2 | 对前面全部字节计算 CRC16，小端 |

CRC 为逐位右移的反射算法：CRC8 初值 `0x77`、多项式 `0x8c`；CRC16 初值 `0x3692`、多项式 `0x8408`。没有另加 final XOR。请用 `samples/golden-vectors.json` 和已有独立字节断言验证 ArkTS/C++ 实现。

`messages.duml_messages()` 同时处理直接 DUML 和 `3b→e9` / `27→ee`、`51/01` 包裹的内层帧。包裹帧也要校验，不能只搜索 `55` 后当成命令回复。

回复匹配至少检查：来源地址、session、CRC、sender/receiver、command set/id、内层序号和回复标志。同一 seq 但其他接收端的回复不能完成当前请求。

## 4. 可靠传输与三种序号

对应 `reliable_transport.py`、`routing_sequences.py`、`flight_controller._send/_service_transport`。

1. **DUML 请求 seq**：匹配请求/回复，u16。
2. **可靠上行序号**：以 seed 为基准，每包加 8，u16 回绕；未确认窗口最多 32 包。
3. **应用路由 counter**：持久化 u32；其低 16 位同步到包裹帧 seq，完整值写进 trailer，再重算 CRC16。它跨进程重启继续增长。

可靠 `05` 上行：16 字节外层头，8–9 放 previous、10–11 放本包序号；接着 4 字节扩展（计数、`01 00 00`），20 起为 DUML。

收到 `01` 后，从原始字节 24–25 读取上行累计确认位置；拒绝倒退、越过已发送范围或不符合步进的确认。重传间隔 0.15 秒，超过 1 秒仍未确认即结束连接；重传发送**完全相同的原始字节**，不能生成新 seq。

`04` 确认包分别包含 video cursor、连续 channel-3 cursor、已发送 previous。视频游标只前进，channel-3 需要按 8 步进补齐连续段。不要直接用收到的最大序号替代所有游标。

路由 trailer 前缀目前来自本设备证据 `8e338dbb02`，生成规则未完全还原。不能据此声称适用于任意飞机。原始 counter 状态不入 Git；鸿蒙端应迁移其身份核验、区段预留、先落盘再发号和单会话互斥语义。

## 5. 注册初始化

对应 `registration_exchange.py`、`registration_schema.py`、`profiles/neo2-registration.json`。

初始调度（相对会话启动，秒）：

| 时间 | 模板 |
| --- | --- |
| 0 | register、首个 heartbeat |
| 0.05 | info_direct |
| 0.15 | open |
| 0.30 | identity |
| 0.45 | capabilities |
| 0.65、1.8 | info_tunnel |

之后约每 0.2 秒 heartbeat，动态更新远端状态、计数和运行时长。收到飞机注册请求时，必须使用**本次飞机请求的序号**回应；`51/41` channel 列表、身份字段有专门解析和验证。未知请求只记录，不随便使用旧回复。

设备查询是 `03/34` 空 payload。启动基础查询的四个目标为 `0e/1f/a2/00`。初始化只有在机型设备回复经过验证、且视频数据新鲜时才完成。握手短包通过不表示注册完成。

## 6. 起飞、降落与八方向

| 动作 | 内层命令 |
| --- | --- |
| 起飞 | `02→03`，`03/2a`，payload `01` |
| 降落 | `02→03`，`03/2a`，payload `02` |
| 四轴 | `02→a9`，`01/0a`，完整 payload 28 字节 |

四轴按 roll、pitch、throttle、yaw 顺序，从 payload **bit 24** 开始各占 11 位。中位 1024，当前动作使用 ±335：

| 方向 | 字段 | 值 |
| --- | --- | --- |
| 前进 / 后退 | pitch | 1359 / 689 |
| 上升 / 下降 | throttle | 1359 / 689 |
| 左移 / 右移 | roll | 689 / 1359 |
| 左转 / 右转 | yaw | 689 / 1359 |

其余三个轴保持 1024。payload 20–22 为 u24 counter；保留其余观测字段。完整常量见 `neutral_stick.NEUTRAL_PAYLOAD`；初期短帧见 `initial_010a.INITIAL_PAYLOAD`，二者不要混淆。

默认动作 0.5 秒、最长 10 秒；这是持续设置轴值，结束恢复中位，不是飞机自行执行的“飞 N 米”导航指令。实际距离依赖速度、环境与标定。连接保持与周期中位帧必须持续，不只发送一次动作报文。

## 7. 原生环绕

对应 `circle_protocol.py`、`native_circle.py`。

| 步骤 | receiver / 命令 | payload |
| --- | --- | --- |
| 选择环绕 | `17` / `03/f9` | `878867a305000000` |
| 写半径 | `92` / `03/f9` | `46932703` + float32 小端米数 |
| 读半径 | `92` / `03/f8` | `46932703` |
| 启动 | `92` / `23/13` | `010500` |
| 停止 | `92` / `23/15` | **长度为 0**，不是单字节 `00` |

先回中、核对模式回显、核对半径写入回显和独立读回；有任一步失败就不启动。代码接受 2–10 米，只有 2 米电脑启动已有实飞证据。读取浮点用绝对误差 `1e-5` 比较。

任务状态 `23/14` 是当前观察到的 5 字节，`0505000100` 曾对应执行阶段；不要推断完整枚举。`0a/bc`、`0a/95` 候选框不等于已验证主体锁定。原生启动可能自行起飞，启动回复 `00` 只表示请求回复。

## 8. 视频与遥测

`video_packets.VideoAssembler` 只组帧，不解码：外层 16 字节后有 4 字节分片前缀，视频内容从 raw[20:] 开始。frame id=raw[16]，count=raw[17]&0x7f，part=((raw[18]&0x1f)<<1)|(raw[17]>>7)。**raw[17] 高位是分片编号的一部分，不是可直接丢弃的 FEC 标志。** 仅完整组帧输出，限制积压并处理重复、冲突和过期。

历史视频是 HEVC Annex-B。解码器、VPS/SPS/PPS 处理、参考链恢复和显示由鸿蒙端另做；这里不包含电脑解码修复算法，不能把本组帧器当成完整播放器。

`landing_status.py` 从校验后的 `03/43` 遥测读取电机和空中标志等字段。字段偏移与本机样本绑定；不把降落 ACK 或某一个高度候选值当作已触地。
