# 图传逐层诊断

目的：在一次 PC 跟随过程中，同步记录网卡视频包、程序实际收到的视频包及队列接收结果、完整视频帧和解码进度。仅增加诊断记录，飞机仍由操作者逐条控制，不会自动起飞或启动跟随。

## 一次启动

飞机落地，退出旧控制台和手机 DJI Fly 的飞机连接，把电脑连接飞机 Wi-Fi。本轮不需要 USB 手机。

以**管理员身份**打开 PowerShell，执行：

```powershell
# 请先切换到本仓库根目录
python .\extras\diagnose_follow_layers.py --capture
```

网卡捕获需要 Windows 管理员权限。工具不会自行弹出提权窗口。默认不带 `--capture` 仅显示帮助；若不能确认 pktmon 空闲则退出，不会停止已有抓包。

工具启动网卡捕获后自动打开原来的交互式跟随控制台及浏览器视频地址。依次输入：

```text
准备
跟随
确认
```

缓慢走几步并观察预览。画面一旦冻结，记一下大概时间，再输入 `停止`，确认悬停后输入 `降落`，目视确认落地后输入 `退出`。若画面一直正常，也在短时跟随后停止、降落、退出。不要在飞机仍飞行时切换电脑网络。

无需再单独运行follow_console或另外启动pktmon。诊断入口退出时会停止它自己启动的捕获、转换格式、保存配对信息，并自动进行离线比对。它只添加/删除本次自己的命名筛选器，不清理其他筛选器。

## 保存内容

终端打印的 `captures/video-layer-日期-时间-编号/` 目录：

- `nic.etl`、`nic.pcapng`：pktmon网卡捕获，完整包，512 MiB循环上限。
- `session.json`：本轮时间、捕获状态及程序原始记录路径。
- `comparison.json`：逐层对照结果，成功配对时自动生成。
- `pktmon-before.txt`、`pktmon-stop.txt`：网卡捕获状态及停止时输出，供检查事件丢失/覆盖。

对应 `captures/video-diagnostics/` 中：

- `.udp.bin`：接收到的每个视频UDP原始数据和视频队列是否接收；独立后台写入，最多128 MiB。
- `.udp.summary.json`：写入是否完整、是否到上限、诊断队列是否丢弃等。
- `.hevc`、`.jsonl`：实际完整帧和解码结果；沿用原来的大小与条数上限。
- `.hevc.summary.json`：拼包/解码诊断是否完整或到达上限。

原有飞行会话记录仍保留。操作完成后，把终端打印的诊断目录或 `session.json` 路径告诉我即可。

## 如何判断

- 网卡有某个完整包，而完整的程序收包记录没有：定位到网卡观测之后、视频提交之前，再核查系统收包及程序过滤。
- 程序记录明确显示视频队列拒绝：确认是视频队列丢弃。
- 程序已接受完整分片，实际完整帧却不匹配：核查工作线程、拼包超时及帧分组；同时做独立分片清点，并不直接把差异认作代码错误。
- 各层传递一致但仍缺参考帧：继续核对网卡侧的源流缺口、采集事件丢失和解码行为；不能仅据此断言无线丢包或飞机没发。

报告只比较同一会话的共同时间窗口，排除两端边界各1秒，并按原始包哈希去重，以减少网卡重复观测的影响。诊断自身丢数据、达到上限或时间不重叠时会明确标为不完整，不据此判定丢失层级。独立分片清点采用2秒分组窗口，仍需结合原始包核实帧号复用；它提供候选线索，不证明协议解析已完全正确。
